## Findings (whole chunk)

1. **Info — memory.rs:40-51: reads /proc/meminfo, spawns sysctl to learn RAM size.** `std::process::Command::new("/usr/sbin/sysctl").args(["-n", "hw.memsize"])` (macOS), `/sbin/sysctl -n hw.physmem` (FreeBSD), `/proc/meminfo` (Linux). Absolute paths, constant args, output parsed to an integer used only to size the cache (RAM/4 clamped 256 MiB..1.5 GiB; `LIGHTCRAFT_MEMORY_MB` overrides). No branch changes behaviour on low RAM beyond the clamp: not sandbox evasion.
2. **Low (robustness, not malicious) — preset_import.rs:64: zip inflate limit trusts the entry's declared size.** `decompress_to_vec_with_limit(data, usize_.max(1) * 2 + 1024)` where `usize_` is the attacker-controlled 32-bit uncompressed size, so a crafted preset .zip/.mplumpack can make the importer allocate up to ~8 GiB per entry (memory DoS on user-initiated preset import). No code execution or file access.
3. **Info — library.rs:344 + smart.rs:137-160: a library's prefs.json can relocate the smart-previews folder.** `smartPreviewsDir` from the library's prefs redirects proxy writes; migrate(Discard/Move) only touches `*.lcsp` files there, and check_writable never creates parents. A shared/hostile library could at most make LightCraft write/delete `.lcsp` proxy files in another folder. Not exploitable for photo destruction.

Re-encountered known issues (not re-investigated): SAM 3 http mirrors (segment/download.rs via lightcraft_segment::fetch, logged in doc.md/R1).

Destructive paths checked (focus C): import Move (source removed only after verified copy + catalog commit + persist, never overwrites; import.rs/import_move.rs), rename/move (hard-link + unlink never replaces, rollback; rename.rs), sidecar writes (merge, `.bak` copy before replacing unreadable file; sidecar.rs), sync "remove missing" (catalog flag only; sync.rs), Lightroom import (Add mode, source catalog read-only, sidecar auto-write suppressed), archives/indices/caches confined to the library folder with exact-name matching, model downloads (pinned URLs + sha256, delete only own staging files). No code path deletes or overwrites user photos outside an explicit user action, and none touches files the user did not choose.

## Conclusion

Verdict for R3-engine-b: **clean**. 35/35 files reviewed (preset_import.rs re-checked after the interrupted run). Network only for user-initiated, acknowledged model downloads from pinned const URLs with sha256 (faces, denoise, SAM 3 via env/user mirrors) and an env-gated loopback-only SAM worker. One process spawn (constant sysctl for RAM size). No persistence, obfuscation, hidden triggers, sandbox detection, data exfiltration, or unsafe code. Several protective guards (refuses home/whole-drive import, originals.rs write guard, create_new everywhere originals are near).
